Auth · RLS · RBAC · 2–3 dias de integração

O fim do "Marco" hard-coded em todo movimento

Hoje a função SQL checkout_projeto aceita um parâmetro p_registrado_por que é sempre 'Marco' hard-coded. O sistema não sabe quem fez o quê. Esse repo entrega o pacote completo: perfis, papéis, policies RLS e isolamento por tenant — tudo que falta pra virar produto.

MIT Supabase · Postgres RLS + RBAC github.com/point-source/supabase-tenant-rbac ↗
O problema hoje

Sistema sem identidade = sistema sem auditoria

  • movimentacoes.registrado_por é literalmente o texto "Marco" em toda linha
  • Migration 00003_auth_profiles.sql existe mas a UI nunca foi plugada
  • Sem isolamento por tenant — se um segundo cliente entrar, dados misturam
  • Não dá pra abrir o sistema pro cliente do Marcelo ver o projeto dele (não há "self-service")
  • Risco LGPD: dado pessoal sem dono identificado em audit trail
O que ganhamos

Padrões prontos pra copiar e colar nas nossas 7 migrations

  • Tabela profiles + roles (Owner, Admin, Operador, Cliente) com FK pra auth.users
  • RLS policies modelo pra cada tabela — items, serial_numbers, projetos, movimentacoes, lotes
  • tenant_id em app_metadata — sem JOIN nas policies → query rápida
  • Storage bucket policies (críticas pro upload de fotos de manutenção)
  • Login via magic link Supabase (sem senha → sem reset)
  • Auditoria real: cada movimento sabe quem operou, com email

Veredito

É o prerequisito pra qualquer feature B2B daqui pra frente.

Enquanto registrado_por = 'Marco', o sistema é demo. Resolver isso destrava: cliente self-service, multi-funcionário, audit trail real, segurança LGPD. Faz mais sentido pagar essa dívida agora do que depois de 6 meses de dados sujos.
