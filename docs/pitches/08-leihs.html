Estudar · Workflow de aprovação

O fluxo de "cliente pede, gestor aprova" em produção

leihs é sistema de lending pra universidades suíças e alemãs — operação real, anos no ar. O ouro pra MMD não é a stack (Ruby/Clojure), é o workflow de reservation: reserva → aprovação → entrega → retorno → conferência. Cada passo tem estado, prazo e ator.

GPL · só leitura Ruby · Clojure · React Reservation workflow github.com/leihs/leihs ↗
O que ainda não fizemos

Hoje o MMD assume que projeto criado = aprovado

  • Não há etapa de "cliente solicita, Marcelo aprova" — todo projeto entra direto em PLANEJAMENTO
  • Se Marcelo quiser deixar funcionário criar projeto sob aprovação, falta o workflow
  • Cliente externo via self-service não consegue solicitar nada — só Marcelo cria
  • Sem estado "REJEITADO" com motivo — toda recusa some no WhatsApp
O que extrair

O state machine de reservation que falta na nossa status_projeto_enum

  • SOLICITADO → cliente/funcionário pediu, aguarda gestor
  • APROVADO → Marcelo deu OK, vai pra fila
  • REJEITADO → recusa com motivo registrado
  • ASSINADO → cliente confirmou contrato/orçamento
  • EM_CAMPO (já temos)
  • DEVOLVIDO_PARCIAL → algum equipamento voltou, falta outro — não temos isso
  • FINALIZADO (já temos)
  • Notification em cada transição: WhatsApp/email pro ator responsável
  • Audit log do workflow: quem aprovou, quando, com qual comentário

Onde divergir

O que não cabe na nossa operação

  • leihs é pra empréstimo gratuito de universidade — não tem orçamento/cobrança
  • Tempo de empréstimo lá é curto (1–3 dias) — MMD pode ter projeto de 2 semanas
  • Stack 100% diferente — não copiar arquitetura, só conceito
